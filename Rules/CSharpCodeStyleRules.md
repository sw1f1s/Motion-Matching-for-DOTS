# C# Code Style Rules

## Type member order

- Внутри класса/структуры сначала общим блоком идут константы `const` и поля `static readonly`, выше остальных полей, в том числе публичных. Это относится и к непубличным полям без явно указанного модификатора доступа, и к полям вложенных типов. Затем идут остальные поля. Локальные константы остаются внутри своих методов.
- После полей идут свойства, getters/setters и expression-bodied properties.
- После свойств идут конструкторы.
- После конструкторов идут public instance methods.
- После public instance methods идут private instance methods.
- Остальные static members размещать в конце соответствующего типа. Константы `const` и поля `static readonly` — исключение: их не переносить вниз к статическим методам и свойствам.
- При перестановке полей проверять зависимости статических инициализаторов и сохранять порядок зависимых вычислений. Не менять значения, атрибуты или условия компиляции ради порядка объявления.

## Unity Inspector and encapsulation

- Поля, настраиваемые через Unity Inspector, объявлять `private` с атрибутом `[SerializeField]`. Не делать поле `public` ради отображения в инспекторе.
- Если значение должно быть доступно другим объектам, предоставлять публичное свойство с публичным getter и приватным setter: `public Type Name { get; private set; }`. Если setter не нужен, использовать свойство только для чтения над приватным сериализуемым полем.
- Для сериализации auto-property атрибут ставить на backing field: `[field: SerializeField] public Type Name { get; private set; }`.
- Не открывать публичный setter ради настройки runtime-компонента извне. Если изменение является частью API, предоставлять отдельный метод, который сохраняет инварианты объекта. Исключение — сериализационные компоненты и их настройки: для них действуют правила ниже.
- При переименовании сериализуемого поля обновлять имена в существующих конфигах, сценах, префабах и JSON-фикстурах в той же правке. Сохранять все значения и ссылки, сверять данные до и после повторного импорта. Не оставлять `FormerlySerializedAs` в коде проекта.

```csharp
[SerializeField] private float _drawDistance = 80f;

public float DrawDistance => _drawDistance;
```

Или, если нужен приватный setter:

```csharp
[field: SerializeField] public float DrawDistance { get; private set; } = 80f;
```

## Serializable settings

- Настройки и data-only контейнеры, сериализуемые через auto-properties, используют `public Type Name { get; set; }` и `[field: SerializeField]`. Поля MonoBehaviour и ScriptableObject для Inspector остаются private с `[SerializeField]` и read-only публичным доступом.
- Значения по умолчанию задавать в property/field initializers. Объекты настраивать через object initializer; не добавлять конструкторы, которые только присваивают настройки.
- При переименовании сериализуемых полей обновлять сцены, префабы, конфигурации и JSON-фикстуры в той же правке. Сохранять значения и ссылки, проверять их после повторного импорта.
- Публичные настройки не делают ECS-компоненты managed. Runtime-данные преобразовывать в unmanaged structs и BlobAsset при создании сущности или запекании.

## Asynchronous runtime code

- Для асинхронной работы в runtime использовать `UniTask` и `await`. Если такая работа добавляется в пакет, явно объявить необходимую зависимость; не рассчитывать на пакеты потребителя. Editor baking использует стандартный `Task`, frame-dependent PlayMode tests — Unity 6 `Awaitable`.
- Не добавлять планировщики на `IEnumerator`, Unity-корутины и обёртки `UniTask.ToCoroutine`.
- Привязывать отмену к lifecycle владельца. При выключении, сбросе или уничтожении объекта завершать работу с ресурсами до их освобождения.

## Nested types

- Не создавать новые nested classes/structs/enums внутри класса, кроме структур `IJobEntity`, описанных ниже.
- Вспомогательные классы, тестовые fakes/probes и DTO выносить в отдельный `.cs` файл рядом с местом использования.
- Структуры `IJobEntity` объявлять вложенными `partial struct` внутри использующей их ECS-системы, в том же `.cs` файле. Не выносить их в отдельные файлы. Методы, специфичные для job, размещать внутри этой структуры. Это явное исключение из запрета nested types.
- Остальные исключения допустимы только для generated/external code, который не редактируется руками.

## Tests

- Тесты хранить в `Assets/Packages/com.collint.mmd.samples/Tests`, разделяя по режиму (`EditMode`/`PlayMode`), подсистемам и фичам. Вспомогательные классы размещать рядом с соответствующими тестами, тестовые assets — в их папке `Fixtures`.

- Для UI-кода автоматические тесты не писать; UI проверять только вручную в Unity.
- Для interface dependencies в unit/service tests предпочитать `NSubstitute` вместо ручных fake/mock-классов; необходимая библиотека относится только к тестовым assembly, а не Runtime.
- Ручной fake/probe допустим только когда нужен stateful simulator, protocol peer, fake ECS world или другой объект с нетривиальным поведением, которое плохо выражается substitute-настройками.
- Новые ручные test doubles не делать nested types; выносить их в отдельный `.cs` файл рядом с тестом.
- Обычные async-сценарии писать стандартными NUnit tests: `[Test] public async Task ...`. Не использовать `[UnityTest]`, `IEnumerator` и `UniTask.ToCoroutine` только ради ожиданий; для ожидания использовать `await`.
- `[UnityTest]` допустим только когда тест действительно проверяет frame-by-frame PlayMode/coroutine-specific поведение Unity.

## Generated code

- Generated-файлы не редактировать руками. Если нужно изменить результат, править source types/config и запускать соответствующий codegen.
- Если генерация кода завершилась ошибкой, исправлять source types/config или настройку проекта, а не generated output.
- Generated output включать в изменения только как результат соответствующей генерации.

## API boundaries

- Публичный Runtime API MMD использует типы пакета и объявленных Unity-зависимостей. Не включать в его сигнатуры типы Editor, Sample или приложения-потребителя.
- Контракты и данные подключения размещать в соответствующей Runtime-области. Не создавать отдельную API assembly только ради формального разделения.
- Editor и Sample используют публичные контракты Runtime. Runtime не обращается к их реализациям; внешние зависимости передавать явно.
- Общие enum-ы и структуры публичного контракта хранить рядом с данными своей области. Не дублировать одни и те же данные между слоями без необходимости.

## ECS components

- Все реализации `IComponentData`, включая cleanup-компоненты, объявлять unmanaged структурами. Не использовать class-компоненты и поля с managed-ссылками; сервисы передавать системам через инжект.
- Ссылки на Unity-объекты внутри ECS-компонентов хранить через `UnityObjectRef<T>`, где `T : UnityEngine.Object`. Для интерфейсного API использовать `UnityObjectRef<UnityEngine.Object>` и свойство, возвращающее интерфейс; конструктор проверяет, что реализация — живой Unity-объект. Не вводить отдельный реестр представлений для доступа к этим ссылкам.
- Разыменовывать `UnityObjectRef.Value` и вызывать методы view только на главном потоке, вне Burst/jobs. `BlobAssetReference` не использовать для managed-ссылок. Освобождение view выполняет cleanup-система при удалении владельца и в `OnDestroy` мира; автоматического вызова `IDisposable` для component structs нет. Не удалять и не перезаписывать владеющий cleanup-компонент до освобождения ресурса.

## Required invariants

- Не использовать `?.`, `??` и fallback-значения для обязательных dependencies, singleton/state entity и других инвариантов, которые к этому месту уже должны существовать.
- Обязательные зависимости проверять при настройке владельца. Их отсутствие — явная ошибка конфигурации; не скрывать её в каждом обновлении.
- Обязательные зависимости обычных runtime/service-объектов передавать через constructor без optional/default параметров.
- Unity Entities systems получают ECS-зависимости через SystemAPI/EntityQuery и OnCreate. См. `SimulationFeatureDevelopmentRules.md`.
- Если инвариант нарушен, код должен падать явно или читать значение напрямую, а не скрывать ошибку дефолтами вроде `0` или `null`.

## Lifecycle

- Если `InitAsync`/`Init` создает объекты, подписки, включает input/actions или меняет lifecycle flags, `Reset` обязан откатить это состояние: отписаться, выключить/освободить созданные объекты, сбросить runtime counters/state и вернуть сервис в состояние, из которого его можно заново инициализировать.
- `Reset` не должен помечать сервис как disposed. `Dispose` должен переиспользовать reset/cleanup-логику и дополнительно выставлять disposed-флаг.
- Не оставлять `Reset` пустым, если сервис имеет состояние, созданное или включенное в `InitAsync`/`Init`.

## Formatting

- Свойства интерфейсов и auto-properties с `get;`, `set;`, `init;` оформлять в одну строку: `World World { get; }`, `public bool IsRunning { get; private set; }`. Модификаторы доступа и initializer сохранять. Accessors с телом и логикой не сворачивать.
- Пустые конструкторы оформлять с телом `{ }` на строке объявления: `public MotionSettings() { }`. Это также относится к конструкторам с `: base(...)` или `: this(...)`. Тела с операторами или комментариями не сворачивать.
- Тела `if`, `else`, `for`, `foreach`, `while`, `do`, `using`, `lock` и `fixed` всегда оформлять блоком `{ ... }`, даже для одного оператора. Операторы внутри блока начинать со следующей строки.
- Каждый оператор писать на отдельной строке. Не объединять несколько объявлений, присваиваний или вызовов через `;` в одной строке. Разделители в заголовке `for` остаются в заголовке.
- Не сворачивать тела методов, циклов, условий и `try`/`catch`/`finally` в одну строку. Открывающая скобка остаётся на строке заголовка, содержимое и закрывающая скобка — на отдельных строках.
- Короткие вызовы методов и конструкторов писать в одну строку вместе с аргументами.
- Переносить аргументы на несколько строк только когда строка становится слишком длинной или содержит длинную лямбду/object initializer/named arguments.

## Performance attributes

- Маленькие методы helper-ов, extension-методы и thin-wrapper методы, которые вызываются из update/hot path, помечать `[MethodImpl(MethodImplOptions.AggressiveInlining)]`.
- Для такого атрибута добавлять `using System.Runtime.CompilerServices;`.
- Не ставить `AggressiveInlining` на большие методы, builders/factories с аллокациями коллекций, IO/network calls, codegen и editor-only tooling, если нет отдельной причины.
